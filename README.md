# Проект Тестовое Задание - Backend приложение

В проекте реализовано backend-приложение с собственной системой аутентификации и авторизации пользователей, а также с разграничением прав доступа к данным.

### Запаск проекта 
* Установить зависимости: `pip install -r requirements.txt`
* Войти в виртуальную среду: `source venv/bin/activate`
* Запустить миграции: `python manage.py migrate`
* Запустить сервер: `python manage.py runserver`

### Основной функционал:
* Регистрация  
* Авторизация(login)
* Выход из системы(logout)
* Обновление данных профиля
* Мягкое удаление аккаунта(пользователь становится неактивным, но пользователь остается в базе)


### Разграничение прав доступа
В проекте реализована собственная система ролей.
При выполнении миграций автоматически создаются три роли:
* admin
* manager
* user

Каждому пользователю назначается одна из этих ролей.
Поведение системы и доступ к API-ресурсам определяется ролью.

### Готовые тестовые пользователи
#### Администратор
* email: admin@mail.ru

#### Менеджер
* email: manager@mail.ru

#### Пользователь

### Права доступа 
#### Admin
* просмотр списка объектов
* просмотр конкретного объекта
* редактирование данных объекта
* просмотр списка пользователей
* изменение роли пользователя (на manager или user)
#### Manager
* просмотр списка объектов
* просмотр конкретного объекта
#### User
* просмотр списка объектов

### Обработка ошибок доступа
* 401 Unauthorized — если не удалось определить пользователя (нет токена, токен недействителен и т.п.)
* 403 Forbidden — пользователь авторизован, но его роль не имеет достаточных прав для доступа к запрашиваемому ресурсу

### Механизм авторизации
Для определения аутентифицированного пользователя используется модель AccessToken, хранящая токен с привязкой к пользователю.
Каждый запрос проходит проверку авторизации и роли пользователя, после чего принимается решение о доступе к ресурсу.


Согласно условиям тестового задания, приложение не должно использовать стандартные Django/DRF механизмы аутентификации, авторизации и сериализации “из коробки”.
Поэтому:
* не использовались классы представлений (APIView, generics и т.п.)
* не использовались сериализаторы DRF
* логика обработки данных реализована вручную
* для функций представлений применялся декоратор @api_view, обеспечивающий базовую работу.
